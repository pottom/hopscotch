# internal/notify

## Purpose

Native OS desktop notifications (macOS/Linux/Windows) on meaningful tunnel/VPN state transitions: unexpected disconnect, recovery, and auto-pause after repeated failures. Gated by `config.NotificationsConfig`; off by default.

## Ownership

`notify.go` (`Notifier`, wraps `github.com/gen2brain/beeep`), `watcher.go` (`Watch` polling loop, `diff` transition state machine), `assets/icon.png` (notification icon, rasterized from `docs/logo.svg`).

## Local Contracts

- `Notifier` methods never return an error and never panic on delivery failure (no notification daemon on a headless Linux box, a failing `osascript` call, etc.) — every failure is logged at Debug level and swallowed. This must never affect the tunnel/VPN control loops.
- `Watch` is a standalone poller of `TunnelStatter.AllStats()` / `VPNStatter.AllStats()` (the same accessors the TUI and web UI SSE already poll every second), **not** a hook into `tunnel.go`/`vpn.go`'s status-mutation call sites. Reason: `tunnel.go` mutates `Status` through three different code shapes (a `setStatus()` helper, two inline `atomic.Value` stores, and one full `Stats{}` struct literal that bypasses both) — hooking all of them uniformly would mean restructuring `Run()`'s hot loop in a package whose own AGENTS.md asks to keep tunnel/vpn pause logic in sync, for a purely additive notification feature. The poller needs zero changes to `internal/tunnel` or `internal/vpn`. Do not "simplify" this back into event hooks without re-deriving this tradeoff.
- `diff` (in `watcher.go`) is a pure function of `(previous tracked state, seen bool, current snapshot) -> (event, next tracked state)` — keep it free of I/O so the transition rules stay unit-testable without `beeep` or a ticker.
- One notification per state-machine edge, not per poll tick: a flapping tunnel/VPN (repeated `Connecting` during a retry loop) must only fire one "disconnected" notification until it actually recovers; auto-pause only re-fires after a `Resume()`.
- A manual pause (`Status == Paused`, `AutoPaused == false`) is a distinct, non-notifying bucket — it must not be folded into the "down" bucket (which would fire a spurious disconnect notification) nor into the "auto-paused" bucket.
- "Reconnected" only fires if a "disconnected" was actually sent for that down period — the first-ever connect at process startup must not notify (seeded via the `seen` flag in `diff`). `trackedState.wasDown` (down as of last tick, regardless of whether it was notified) and `notifiedDown` (a "disconnected" was actually sent) are deliberately two separate fields, not one bool: seeding must set `wasDown` from a down startup snapshot (so a slow multi-tick initial connect, e.g. a VPN handshake spanning more than one poll, isn't mistaken for a fresh disconnect on tick 2) but must *not* set `notifiedDown` (so the eventual successful connect doesn't fire a "reconnected" for a disconnect the user was never told about). Collapsing these back into one bool reintroduces one bug or the other — see `TestDiff_SlowInitialConnect_NoPhantomDisconnect` and `TestDiff_Reconnect_OnlyAfterADisconnectWasNotified`.
- `Watch`'s ticker loop skips both `AllStats()` calls entirely (`continue`) when `n.Config().Enabled` is false, the shipped default — avoids a per-second lock+alloc+copy for a poller whose output is discarded anyway. Tracked state is left untouched while skipped, not reset; on re-enable, `diff` compares against whatever was last observed before disabling; a name unseen since a real transition happened while disabled will produce one correct catch-up event on the next enabled tick.
- `Notifier.Suppress(kind, name)` marks a 15s window (`suppressWindow`) during which `Watch` drops any event for that name instead of firing it — used by `internal/admin`'s reconnect/resume handlers to mark a manual action before triggering it, since a forced reconnect or a resume-from-manual-pause both drive `Status`/`State` through the same `Connecting` transient a real failure would, and the watcher (which only sees polled snapshots, not intent) can't otherwise tell them apart. **Found via live testing against a real daemon, not by inspection** — the bug produced a real "disconnected"/"reconnected" notification pair for a manual admin-API reconnect. `Suppress` and `suppressed` are both nil-receiver-safe and no-op when `cfg.Enabled` is false (each checks it directly, not just incidentally true because of how callers happen to gate them), so `internal/admin` can call `Suppress` unconditionally without checking whether notifications are on.
- `cfg.Sound` switches `send` from `beeep.Notify` to `beeep.Alert` — same signature, same delivery backends per OS, the only difference is `Alert` also plays the OS default notification sound (macOS/Linux: a "bell"/default sound hint on the same osascript/terminal-notifier/dbus call; Windows: same toast, with sound). Confirmed live on macOS. Default off, like the rest of the config.
- `assets/icon.png` is a derivative build asset, not a canonical source — regenerate it from `docs/logo.svg` with `magick -background none -density 384 docs/logo.svg -resize 256x256 internal/notify/assets/icon.png` whenever the logo changes (see `docs/AGENTS.md` for the canonical SVG). It's embedded via `go:embed` and passed to `beeep.Notify` as the icon; Linux (D-Bus) and Windows (toast) should show it (unverified — no native dev access to either OS). **On macOS it never shows, and this isn't fixable from here**: confirmed by direct manual test on macOS 26.5.1 that even with `terminal-notifier` installed *and* granted notification permission in System Settings, its `-appIcon`/`-sender` icon override has no effect — modern macOS blocks custom notification icons for unbundled CLI/daemon tools. The only real fix (shipping hopscotch as a signed `.app` bundle and posting via `UNUserNotificationCenter`) needs cgo and a bundle identity, which conflicts with the `CGO_ENABLED=0` single-runner cross-compile pipeline (`build.sh`) — deliberately not pursued; the notification text alone is still correct and sufficient on macOS.

## Work Guidance

Config is live-editable from both UIs via the admin API's Settings tab (`internal/admin/notifications.go`, `PUT /api/notifications`) — see `docs/DESIGN.md`. `Notifier.SetConfig` is what makes this take effect without a restart; any future field added to `config.NotificationsConfig` needs a matching field in `admin.NotificationsJSON`, the TUI's `settingsRows`, and the web UI's checkbox list to stay in parity (see `internal/tui/AGENTS.md`, `internal/admin/ui/AGENTS.md`).

## Verification

`go test ./internal/notify/...` covers the `diff` transition rules (disconnect, flapping, reconnect, auto-pause cycle, manual-pause exclusion, startup seeding) and the `Suppress`/`suppressed` bookkeeping (active window, expiry+pruning, disabled-config no-op, nil receiver, kind/name scoping). Delivery itself (`beeep.Notify`) and the `Watch`↔`Suppress` integration are only verifiable manually against a real daemon — see `scripts/hs-watch.sh` and the `/debug` skill; confirmed live on macOS for auto-pause, and for the force-reconnect false-positive this suppression mechanism fixes.
