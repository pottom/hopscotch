# internal/vpn

## Purpose

Manages an `openconnect` subprocess per configured VPN: connect detection (stderr watching plus optional `ping_host` polling), backoff reconnect, pause/resume, graceful teardown (`post_disconnect`, DNS/route cleanup).

## Ownership

`vpn.go` (`Connection`: `Run`/pause-resume/state machine), `dark.go` (dark-session detection), `retrypolicy.go` (learned wait after a dark session), `history.go` (session history), `report.go` (`hopscotch vpn stats` summaries), `counters_*.go` (interface packet counters), `manager.go` (`Manager`: owns all `*Connection` by name; `IsConnected`/`IsPaused` are consumed by `internal/tunnel` for VPN gating; `Switch`), `vpncscript.go` (the `--script` wrapper written per VPN), `pushed.go` (what the gateway pushed, recorded by the wrapper), `openconnect.go` (subprocess/arg construction), `process_unix.go`/`process_windows.go` (process-group kill).

## Local Contracts

- Same pre-`Run()` pause-then-restore safety pattern as `internal/tunnel` (`Run()` checks `paused` first, drains a stale `pauseRequest`) — see `internal/tunnel/AGENTS.md`; keep both in sync if this pattern ever changes.
- Several VPNs can be configured at once (e.g. two concentrators into the same network, switched by pausing one and resuming the other), so every signal/kill targets **this** VPN's process only: `terminateProcs`/`killOrphanedProcs` use `pkill -f` with `procPattern` (binary as argv[0], server URL as the last argument — `buildArgs` must keep the server last). Never go back to a name-only `pkill -x openconnect`; it tears down the other VPN, which then restarts and kills this one in turn.
- After a switch every VPN reports the same interface name (Linux reuses `tun0` once the old device is gone), so the name alone never identifies a connection's device. `setTunIface` stores the kernel index next to the name, `flushTunRoutes` flushes only while that index still matches (otherwise it would wipe the newly started VPN's routes), and `runPostDisconnect` clears both so a paused VPN doesn't keep displaying a device it no longer has.
- openconnect prints errors to stderr but progress (`Connected as`, `Set up tun device`) to **stdout**; both are routed into one `os.Pipe` read by `watchOutput`. Keep both pipe ends `*os.File` (not `cmd.StdoutPipe`/an `io.Writer`) — otherwise exec adds a copy goroutine that `cmd.Wait()` blocks on while an orphaned child holds the write end.
- When `ping_host` is set it is the only thing that marks a VPN `connected`; `watchOutput` promotes on `Connected as`/`Established …` only without `ping_host`. After switching between VPNs the session is up long before internal hosts answer (measured 15–35 s), and promoting early makes tunnels dial into an unrouted network and burn their auto-pause budget.
- `connect_timeout` (default 30 s) bounds how long `ping_host` may stay unreachable after launch. A session whose tunnel sends but receives nothing is "dark" (`dark.go`): `pollPingHost` ends it early from the Linux interface counters (`gatewayDark`, ~15 s) or at the timeout, and sets `lastAttemptDark`. Every attempt is recorded by `recordSession` into the Manager-shared `sessionHistory` (`history.go`: start context + outcome ok/dark/failed/cut + assigned IP, JSON lines in the cache dir, 500 records / 30 days, never errors). After a dark attempt `Run()` asks `chooseDarkRetry` (`retrypolicy.go`) for the wait instead of the exponential backoff: it buckets past attempts that followed a dark one by how long was waited (15 s / 30 s / 1 m / 2 m — manual pause/resume retries count too), estimates each success rate with a uniform prior and a 7-day half-life, and picks the lowest expected recovery time `(wait + dark-attempt cost) / p`, with 10 % exploration of under-sampled waits and the 15 s default below 8 effective observations. The decision's `Reason` goes into `lastError` (both UIs), its `Detail` into the log; `hopscotch vpn stats` shows the same numbers. `darkStreak` (reset on connect, resume, force reconnect) only drives the hard floor: from 6 dark attempts in a row at least 2 min. `hold_dark_session` (off by default, unproven) keeps the dark session open for that floor instead (`heldCooldown`). All of this only ever delays the **automatic** retry: a manual pause, resume or force reconnect is acted on immediately, in every wait. There is deliberately no rate limit on session starts any more — the shared "session gate" (3 starts / 2 min, 3 s settle after another VPN's start) made every manual switch wait and was removed on 2026-09-19 after measuring 13 switches between the two 4ig VPNs (make-before-break, and pause → 1/30/60 s → resume, on v0.9.1 and v0.12.0): all connected in 1–4 s, one took 17 s because openconnect installed the routes late (tun up, tx 0 for 15 s, then everything at once — which is why the dark verdict waits 15 s and the timeout 30 s), and none was dark. Dark sessions were only ever seen on 2026-09-15 around a burst of ~25 sessions in ten minutes; the learned retry and the streak floor remain the protection for that case. Don't bring back a gate on manual actions.
- The first successful `ping_host` probe marks the VPN connected (a TCP handshake already proves two-way traffic); don't reintroduce a multi-probe confirmation. Measure changes here with `scripts/hs-watch.sh` or a timed pause/resume switch, not by eye.
- openconnect always gets `--script` = hopscotch's own wrapper (`vpncscript.go`, one `vpnc-<name>.sh` per VPN in the cache dir, rewritten at every start, `vpnc_script` config picks the system script it runs; `--script` in `extra_args` is rejected by config validation). The wrapper runs the system vpnc-script and then: on connect points every `CISCO_SPLIT_INC` route at this session's tunnel (`ip route replace` / macOS `route change`, falling back to `add`) so the session that came up last carries the traffic on both OSes, and writes `vpn-<name>.pushed.json` (routes, DNS, address, gateway; read by `readPushed`, ignored unless its `tundev` is the current interface, since a SIGKILLed daemon leaves stale files); on disconnect removes only routes still on this tunnel and re-points the routes of every other VPN whose tunnel is still up (the macOS system script deletes by prefix and would take them). Two VPNs into different networks are untouched by any of this: only identical prefixes are ever moved. Test the wrapper with `sh` and fake tools as `vpncscript_test.go` does; never assume bash (macOS runs it with /bin/sh as root through sudo).
- `Manager.Switch(ctx, to)` is the clean switch the UIs expose (`POST /api/vpns/{name}/switch`, TUI `s`, web ⇄): `Resume(to)`, poll `AllStats` until `to` is `StateConnected`, then `Pause` every other connected VPN whose pushed routes overlap `to`'s (`routesOverlap` over `Stats.PushedRoutes`). VPNs into non-overlapping networks keep running. The decision is by route **overlap**, not by `RoutedVia`/`RouteInterface`: on macOS both openconnects re-point the shared routes on every reconnect and race for them (measured 2026-09-19), so which interface owns a route right now flaps; overlap is stable, and once the loser is paused its disconnect hook hands the shared routes back to `to`. When neither side recorded any pushed routes (openconnect without a wrapper), overlap is treated as true so a switch still switches. Timeout = `connect_timeout` + 15 s, after which nothing is touched and `to` keeps retrying. The previous switch (pause A, resume B) could leave the earlier VPN routeless when the later one had replaced its routes, hopscotch restarted it and the fresh session came up dark — the switch avoids creating that fresh session at all.
- `Manager.AllStats` fills `Stats.RoutedVia` when at least two VPNs are connected: for each connected VPN it asks `netcheck.RouteInterface(ping_host)` which interface really carries the traffic (a UDP connect, nothing sent; works the same on Linux and macOS), and when that isn't the VPN's own `TunIface` it names the VPN owning it (or the interface). Both VPNs push the same internal networks, so one of them is always idle — on Linux the later session's `ip route replace` wins, on macOS the earlier session's routes stay — and `ping_host` answers through either, which is why a second connected VPN would otherwise look healthy. The UIs render it as `● connected ⚠ via X` (`docs/DESIGN.md`). Only `AllStats` computes it; `Connection.Stats` alone never sets it.
- No config hot-reload exists for VPNs (unlike tunnels' `ApplyConfig`) — a VPN config change requires a full process restart.
- `connectedAt` is stored as `time.Now().Round(0)` (strips the monotonic clock reading), not raw `time.Now()` — otherwise the displayed "connected since" duration freezes during macOS sleep (monotonic clock doesn't advance while suspended). Same pattern as `internal/tunnel`'s `ConnectedAt`; apply it to any new timestamp captured here for duration display.
- `consecutiveFailures` (`atomic.Int32`) counts connection attempts in a row that never reached `StateConnected` — reset at the same `connectedAt.Load().(time.Time).After(beforeRun)` check that already resets the backoff, and on `Resume()`. When `cfg.AutoPauseThreshold > 0` and the count reaches it, `Run()` triggers the same pause mechanics as the public `Pause()` (mirrors `internal/tunnel`'s identical mechanism — see that package's `AGENTS.md` for the shared rationale: not persisted via `internal/state.PausedTracker`, a deliberate second exception to the admin-handlers-only Pause/Resume contract in `internal/admin/AGENTS.md`, and `Resume()` always resets the counter regardless of pause reason).
- `Pause()`/`pauseLocked()` split, the `pauseMu` mutex serializing pause/resume/auto-pause/auto-resume transitions, `autoPaused` flag, and `Stats().AutoPaused` all mirror `internal/tunnel` exactly (down to the field and method names) — see that package's `AGENTS.md` for the precise rule about which of `Pause()`/`pauseLocked()` to call from where, and for why `pauseMu` exists (a TOCTOU race between a concurrent `Pause()`/`Resume()` and the auto-resume timer's check-then-mutate sequence). Keep both packages' pause/auto-pause code in sync if this mechanism changes in either.
- `cfg.AutoResumeAfter` (seconds, 0 disables) mirrors `internal/tunnel`'s auto-resume cooldown exactly, down to the manual-pause-during-cooldown race guard (re-check `autoPaused` under `pauseMu` when the timer fires, don't call `Resume()` itself to avoid leaving a stale token in the buffered `resume` channel) — see that package's `AGENTS.md` for the full rationale. One difference: this package has no `Clock` abstraction, so the cooldown uses a plain `time.After` rather than `t.clock.After`.

## Work Guidance

Debugging reconnect/timeout behavior: use `scripts/hs-watch.sh` for automated, timed observation instead of watching logs manually — DNS resolve, `ping_host` polling, and backoff timing are easy to misjudge by eye.

## Verification

`go test ./internal/vpn/...`; `scripts/hs-watch.sh` for live reconnect behavior.
